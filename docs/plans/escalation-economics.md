# Экономика эскалации: чтобы плагин экономии контекста не тратил контекст

## Что решает этот план

Зафиксированный инцидент (2026-08-20, живая сессия Claude Code, проект casino):
`Read` файла в **2.4 КБ** отклонён с сообщением на ~1 КБ, при штатном пороге
отказа 50 КБ. Сессия к этому моменту накопила «93 unrouted heavy calls,
619.9 KB» и навсегда застряла на верхней ступени лестницы эскалации.

Разбор показал не один баг, а связку из семи дефектов в контуре
PreToolUse → PostToolUse → tally → лестница. Общий знаменатель: **цена
вмешательства нигде не сравнивается с ценой байтов, от которых оно защищает**,
а счётчик нарушений наполняется поведением, которое сам плагин объявляет
правильным. Ниже — инвентарь дефектов с координатами и фазы исправления.

---

## Инвентарь дефектов

### D1. Floor отказа на ступени DENY — 2000 байт, дешевле самого отказа

`hooks/core/routing.mjs:1477` — на уровне DENY отклоняется любой unbounded
Read файла ≥ `missedRedirectFloorBytes()` = 2000 байт (routing.mjs:1847).
Текст отказа (`readDenyReason` + `escalationNote`) — ~1 КБ, и он входит в
контекст. Модель почти всегда берёт escape hatch (повтор в 120-секундном
окне) — файл входит целиком. Итог для файла 2.4 КБ: **1 КБ отказа + 2.4 КБ
файла + лишний round-trip** против просто 2.4 КБ. Отказ на этой ступени
убыточен для всего диапазона 2–10 КБ.

### D2. Лестница монотонна: сессия не может реабилитироваться

`routing.mjs:353` («tally only grows within a session») и
`escalationLevel()` (routing.mjs:447). Ни роутинг последующих вызовов, ни
подтверждения пользователя, ни время не снижают уровень. 9 вызовов — и до
конца сессии каждый Read ≥ 2 КБ идёт через отказ+повтор. Длинные сессии,
заявленный главный сценарий плагина, получают худший режим перманентно.

### D3. Tally наполняется санкционированным поведением

`describeMissedRedirect` (routing.mjs:1867) считает нарушением любой ответ
`Bash|Read|Grep|Glob|WebFetch|Shell` ≥ 2000 байт без маркера. В том числе:

- **bounded Read с offset/limit** — тот, про который текст отказа обещает
  «goes through unchanged». Проходит, но двигает лестницу: плагин наказывает
  за выполнение собственной инструкции;
- **git-команды** — CLAUDE.md проекта говорит «Bash ONLY for: git, …», но
  `git diff`/`git log` ≥ 2 КБ записывается как missed redirect;
- **вызовы, подтверждённые пользователем через `ask`** — согласие человека
  не помечает вызов как routed;
- **вызовы сабагентов** — pretooluse.mjs:167 распознаёт сабагента
  (`agent_id`/`agent_type`) и отключает для него deny, но в posttooluse.mjs
  проверки нет: чтения Explore-агентов пишутся в общий сессионный tally,
  хотя их байты в основное окно **не входят** (контекст сабагента
  выбрасывается, возвращается только отчёт). Основной цикл эскалируется за
  чужие байты — наиболее вероятный источник «93 вызовов» инцидента.

### D4. Учёт экономии завышен: advisory-решения записываются как savings

`routing.mjs:1493` вешает `redirectMeta` с `bytesAvoided: st.size` на
**advisory**-решение (`action: "context"`): Read разрешается, файл целиком
входит в контекст, а PostToolUse (posttooluse.mjs:119, ветка
`bytesAvoided > 0`) записывает его размер как «сэкономлено»
(category=redirect) и заодно подавляет missed-учёт (`redirectEmitted`).
Достижимо для bounded-чтений больших файлов, для fallthrough при
недоступном MCP и всегда при `CONTEXT_MODE_READ_DENY_BYTES=0`: оператор
выключил enforcement — ctx_stats рапортует экономию на каждом большом
чтении, вошедшем в окно целиком.

### D5. Маркер — одна ячейка на сессию: гонки и ложные savings

`context-mode-redirect-${sessionId}.txt` (routing.mjs:1787) перезаписывается
каждым PreToolUse и потребляется «чьим-то следующим» PostToolUse. При
параллельных tool-вызовах (штатный режим Claude Code) PreToolUse B затирает
маркер A до того, как PostToolUse A его прочитал — учёт приписывается не
тому вызову или теряется. Отдельный случай: маркер отказа (у отклонённого
вызова нет своего PostToolUse) доживает до чужого PostToolUse и записывает
`st.size` как savings — даже если следом retry внёс те же байты в контекст.

### D6. Полный «fine print» в каждом отказе

`readDenyReason` (routing.mjs:322) + `escalationNote` повторяются целиком
при каждом срабатывании: три строки инструкций, имена env-переменных,
tally. На ступени DENY в активной сессии это десятки килобайт инъекций от
самого плагина — статья расхода, которой нет ни в ctx_stats, ни в
BENCHMARK.md.

### D7. Инцидентная сессия работала на устаревшем кэше

Текст ошибки у пользователя — от старой версии `readDenyReason` (без
`ctx_read`). Это профиль отказа из `docs/plans/tool-adherence.md` D0: ключ
кэша плагина — номер версии, номер не двигался. Любая правка этого плана
без bump версии не доедет до установленного плагина.

## Фазы

### P0. Факты (полдня, до любого кода)

1. **Payload сабагента в PostToolUse.** pretooluse опирается на
   `input.agent_id ?? input.agent_type`. Проверить на живом хосте, что эти
   поля реально приходят и в PreToolUse, и в PostToolUse при вызовах внутри
   Agent (временный лог payload в файл через `CONTEXT_MODE_DEBUG`-ветку или
   разовый hook-скрипт). Если полей нет — найти работающий сигнал
   (отличие transcript path у sidechain и т.п.) до начала P1.
2. **`tool_use_id` в payload хуков.** Если хост его даёт — ключ per-call
   маркеров в P4 строится на нём; если нет — fallback:
   `sha256(tool_name + канонический JSON(tool_input))` первые 16 hex.
   Коллизия двух одинаковых параллельных вызовов приемлема.
3. Подтверждено при разборе: `session_events.created_at` существует
   (секундное разрешение, `datetime('now')`) — оконному tally в P3 хватает.

### P1. Санкционированное поведение перестаёт быть нарушением (лечит инцидент)

Все правки — в `describeMissedRedirect` (routing.mjs:1867) и
posttooluse.mjs; Codex-хуки используют тот же `hooks/core/routing.mjs`,
поэтому получают их автоматически (проверить импорты в `hooks/codex/`).

1. **Сабагенты.** В posttooluse.mjs — та же проверка
   `isSubagentContext`, что в pretooluse.mjs:167: для сабагентного вызова
   пропускать весь блок missed-redirect (событие, tally, cost notice).
   Байты сабагента не входят в основное окно — им нечего «пропускать».
2. **Bounded Read.** `describeMissedRedirect` получает исключение через уже
   существующий `isBoundedRead` (routing.mjs:230): вызов с явным `limit`
   не событие. Обещание «goes through unchanged» становится правдой целиком.
3. **Санкционированный Bash.** Прогонять команду через
   `isStructurallyBounded` + короткий allowlist префиксов из routing-правил
   (`git `, `npm install`, `pip install`, `mkdir`, `mv`, `rm`, `ls`). Такие
   вызовы записывать **новым типом события** `sanctioned_heavy` (та же
   data-строка, другой префикс) — видимость в ctx_stats сохраняется, но
   `readMissedRedirectTally` (фильтр по `type: "missed_redirect"`) их не
   считает и лестница не движется.
4. **Подтверждённый `ask`.** PreToolUse при `action: "ask"` пишет per-call
   маркер `ask-{callKey}` (ключ из P0.2). Если PostToolUse этого вызова
   наступил — пользователь подтвердил; вызов учитывается как
   `sanctioned_heavy`, не как нарушение. Маркеры с TTL, зачистка в
   sessionstart по образцу существующих guidance-маркеров.

**Согласованность с аналитикой:** `src/session/analytics.ts:1178` парсит
`^…bytes unrouted` — знаменатель adherence должен исключать
`sanctioned_heavy` симметрично, иначе ctx_stats и лестница разойдутся
(инвариант из комментария к `readMissedRedirectTally`). Правки в обеих
точках в одном коммите.

**Тесты:** `tests/analytics/missed-redirect.test.ts`,
`tests/analytics/routing-adherence.test.ts`,
`tests/hooks/missed-redirect-notice.test.ts` — дополнить кейсами
исключений; новый тест на сабагентный payload в posttooluse.

### P2. Экономика отказа: floor ступени DENY

`routing.mjs:1477`: заменить `st.size >= missedRedirectFloorBytes()` на
отдельный порог `escalationDenyFloorBytes()`:

```
max(16384, CONTEXT_MODE_ESCALATION_DENY_MIN_BYTES)
```

Обоснование числа: цена отказа ~1 КБ входит в контекст всегда, и в
read-to-edit сценарии файл затем входит целиком; отказ должен окупаться с
запасом ≥ 8–16× даже при частичном соблюдении. Диапазон 2–16 КБ на ступени
DENY остаётся на `ask`/advise (существующие ветки routing.mjs:1498, 1511 —
без изменений). Floor учёта (2000) не трогаем — он про телеметрию, не про
enforcement; ветка retry-exempt (routing.mjs:1420) остаётся на floor учёта,
её симметрия — с телеметрией.

**Тесты:** `tests/hooks/escalation-ladder.test.ts` — кейс «DENY-уровень,
файл 2.4 КБ → проходит без отказа», кейс «DENY-уровень, файл 20 КБ →
отказ».

### P3. Лестница перестаёт быть монотонной: окно вместо вечного счёта

Механизм один — **скользящее окно**, а не «кредиты за routed-вызовы»
(второй счётчик неизбежно разъезжается с первым; отвергнуто).

1. `readMissedRedirectTally` (routing.mjs:1908): считать по `created_at`
   две пары чисел — за сессию (для текста уведомлений: «всего за сессию»)
   и за окно `CONTEXT_MODE_ESCALATION_WINDOW_MS` (default 15 мин).
2. `writeUnroutedTally`/`readUnroutedTally`: формат файла расширяется до
   `{count, bytes, windowCount, windowBytes, at}`; старый двухполевой
   формат читается как «всё в окне» (совместимость на время раската).
3. `escalationLevel` считает уровень от **оконной** пары. Затухание без
   новых PostToolUse: если `at` старше окна — уровень SILENT
   (`readUnroutedTally` возвращает null-эквивалент для лестницы, но
   сессионные числа остаются доступны тексту).
4. Комментарий-манифест о монотонности (routing.mjs:344–366) переписать:
   новое свойство — «уровень — функция недавнего поведения; тихое окно
   возвращает сессию к тишине», и оно же ассертится в тестах.

**Тесты:** `tests/hooks/escalation-ladder.test.ts` — снять ассерты
монотонности, добавить: затухание после тихого окна; события внутри окна
двигают уровень; сессионные числа в тексте не сбрасываются.

### P4. Честный учёт: savings только за то, что реально не вошло

1. **D4:** в advisory-ветке (routing.mjs:1493) и во всех
   `action: "context"`-решениях **не** вешать `redirectMeta` с
   `bytesAvoided > 0`. Разрешённый unbounded большой Read — это missed
   (пусть PostToolUse его посчитает), bounded — sanctioned (P1.2).
   `bytesAvoided: st.size` остаётся только на реальных deny.
2. **D5:** маркеры становятся per-call:
   `context-mode-redirect-${sessionId}-${callKey}.txt`.
   - PostToolUse потребляет **свой** ключ (вычисляет из своего payload);
   - маркеры отказов (у них нет своего PostToolUse) добирает зачистка:
     любой PostToolUse подметает чужие маркеры старше ~2 с и проводит их
     как savings отказа;
   - **retry-отмена:** PreToolUse, пропуская повторный Read по
     `readRetryArmed`, удаляет висящий deny-маркер этого пути — байты
     вошли, savings не заявляется. Это закрывает ложные savings у
     deny-then-retry без отрицательных событий в БД.
3. `consumeRedirectMarker`/`writeRedirectMarker` (routing.mjs:1790–1832)
   переписать под ключ; формат строки внутри файла не менять.

**Тесты:** `tests/hooks/read-edit-exempt.test.ts` — сценарий
deny → retry → savings отсутствует; новый тест на два параллельных вызова
(маркеры не перетирают друг друга); тест зачистки stale-маркера как
deny-savings.

### P5. Диета сообщений

1. Полный `readDenyReason` — один раз за сессию (маркер по образцу
   `guidanceOnce`, тип `read-deny-fine-print`). Последующие отказы — одна
   строка: `context-mode: Read redirected — ctx_read(path: …) | повтор
   Read ≤120s для Edit | offset/limit.` Слово «redirected» и готовый
   replacement-вызов остаются в одной строке — контракт ADR-0003
   (routing.mjs:319, контрактный тест читает файл построчно) соблюдён;
   ADR дополнить абзацем о короткой форме.
2. `escalationNote` после первого показа сокращается до
   `N unrouted calls / X KB this session.` — имена env-переменных модель
   уже видела в полной форме.

**Тесты:** контрактный тест ADR-0003; снапшоты в
`tests/hooks/missed-redirect-notice.test.ts`.

### P6. Поставка и закрытие волны

1. **Первым шагом волны** — `npm version patch` (разносит номер по всем
   манифестам через `scripts/version-sync.mjs`); без него ничего из
   P1–P5 не доедет до кэша плагина (D7, см. tool-adherence.md D0).
2. Пересборка бандлов, прогон полного набора:
   `tests/hooks/*`, `tests/analytics/*`, `tests/codex/*` (общий core —
   проверить, что Codex-хуки прошли те же исключения),
   `tests/plugins/plugin-structure.test.ts`,
   `tests/hooks/matcher-coverage.test.ts` (не должны измениться).
3. Запись в `FORK-CHANGES.md` + новый ADR «Экономика эскалации»
   (порог DENY, окно, санкционированные вызовы) — правила теперь
   распределены по трём файлам, ADR фиксирует инварианты.

## Порядок и зависимости

```
P0 ──► P1 (нужен факт о payload сабагента)
P0 ──► P4 (нужен факт о tool_use_id)
P1, P2 — независимы, дают немедленное облегчение инцидентного сценария
P3 — после P1 (окно считает уже очищенную популяцию событий)
P5 — независима
P6 — всегда последняя, version bump — первый коммит волны
```

## Критерии приёмки (реплей инцидента)

Сессия, искусственно доведённая до уровня DENY:

1. `Read` файла 2.4 КБ проходит молча; 20 КБ — отказ.
2. Второй отказ подряд — однострочный, не ~1 КБ.
3. Explore-сабагент читает 500 КБ — tally основной сессии не двигается.
4. `git diff` на 15 КБ — событие `sanctioned_heavy`, лестница на месте.
5. 15 минут без тяжёлых вызовов — уровень возвращается к SILENT.
6. deny → retry: в ctx_stats нет строки savings за этот файл; advisory на
   разрешённом большом Read не создаёт `bytes_avoided`.
7. Два параллельных tool-вызова — учёт каждого приписан своему вызову.

## Не делаем в этой волне

- Не трогаем пороги `ask` для Grep/Glob (routing.mjs:1541+) — их экономика
  не разобрана измерениями, а `ask` дешевле deny на порядок.
- Не вводим «кредитную» модель реабилитации — окно покрывает потребность
  одним механизмом.
- Не меняем формат строки маркера и data-строк событий, кроме нового
  префикса `sanctioned_heavy` — минимизируем связанные правки в
  analytics.ts.

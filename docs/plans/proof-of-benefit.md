# Доказательство пользы: обратный трафик плагина и бенчмарки, которые меряют результат

## Что решает этот план

Две вещи, которых сейчас нет.

**Первая.** Плагин экономит контекст на входе (сырые байты остаются в песочнице) и
тратит его на выходе. Замерено на живом транскрипте сессии `bc3ee44a` (16 вызовов
`ctx_*`, 80 655 симв. возвращено модели): **35,5% этих байтов — строительные леса**,
а не ответ. Из них 14 551 симв. — эхо кода, который вызывающий только что написал
сам и который уже лежит в его окне в блоке `tool_use`. Отдельные вызовы
`ctx_execute` состояли из эха на 74%, 78%, 82%, 86%.

**Вторая.** Ни один существующий бенчмарк не отвечает на вопрос «помогает ли
плагин». `tests/benchmark.ts`, `tests/context-comparison.ts`,
`tests/ecosystem-benchmark.ts` — все фикстурные: программа уже написана,
маршрутизация уже выбрана, остаётся сравнить размер сырых байтов с размером
`console.log`. Это измерение **механизма**. Оно не может ни подтвердить, ни
опровергнуть, что агент с плагином решает задачи так же правильно и дешевле
агента без плагина, потому что агент в этом измерении не участвует.
`tests/latency-benchmark.ts` (Part 4 в BENCHMARK.md) — единственный, который
гоняет настоящий `server.bundle.mjs` по stdio, и единственный, где нашлись
неудобные строки (`ctx_find` возвращает вчетверо больше байтов, чем `rg -l`).

Отсюда два требования, поставленных заказчиком плана, и оба они — про то, чего
фикстурный бенчмарк увидеть не может:

- **Экономия не должна вредить работе агента.** Значит первичной метрикой
  становится правильность, а экономия засчитывается только на задачах, решённых
  верно. Байты, сэкономленные на неверном ответе, — не экономия.
- **Плагин должен работать в субагентах.** Значит субагентский путь измеряется
  отдельной веткой бенчмарка, а не предполагается работающим.

Этот план не пересекается с `escalation-economics.md` (тот про цену вмешательств),
`tool-adherence.md` (тот про то, зовут ли инструменты вообще) и
`improvement-roadmap.md` (тот про retrieval-стек). Он про **обратный трафик самого
плагина** и про **доказательную базу**. Пункт D7 из `tool-adherence.md`
(«сделать соблюдение числом») здесь используется как готовый вход: adherence уже
считается в `src/session/analytics.ts`, его надо не изобретать, а вынести в
бенчмарк.

# Часть I. Инвентарь дефектов

Все числа — измерения, не оценки. Метод указан у каждого.

## D1. Эхо кода возвращается вызывающему

`src/server.ts:1987` — `CODE_ECHO_MAX = 2000`, захардкожен, флага нет.

Комментарий над функцией объясняет назначение: *«provenance survives in indexed
chunks (FTS5 sees the fenced block) so later ctx_search hits remember what ran»*.
Это аргумент за то, чтобы код **индексировать**. Аргумента за то, чтобы его
**возвращать в ответе**, там нет — вызывающий отправил этот код сам полминуты назад.

| | |
|---|---|
| Метод | разбор транскрипта сессии, классификация байтов ответа |
| Цена | 14 551 симв. из 80 655 (18% всего обратного трафика `ctx_*`) |
| Худшие вызовы | 86%, 82%, 78%, 74% ответа — эхо |

Тот же принцип в форке уже изобретён и работает: `ctx_read` при повторном чтении
неизменившегося файла отвечает строкой `unchanged since your last read` вместо
среза (`src/tools/read.ts:508`). Не обобщён на остальные инструменты.

## D2. Тройной учёт команд в `ctx_batch_execute`

Один и тот же факт печатается три раза: блок `## Commands` с дословными командами,
листинг `## Indexed Sections`, и строка `$ <команда>` внутри каждой секции
результата.

| | |
|---|---|
| Цена | 2 662 + 4 043 + 1 479 = **8 184 симв.** за 4 вызова |

Не всё здесь мусор: метки нужны, чтобы позже адресовать секции в `ctx_search`.
Мусор — именно троекратность.

## D3. Футеры и приглашения на второй вызов

`> **Tip:** Results are scoped to this batch only…`, `Searchable terms for
follow-up: …`, `> Showing 3 of 11+ matching section(s)`.

| | |
|---|---|
| Цена | 3 801 (футеры) + 1 827 (`Showing N of M`) = **5 628 симв.** |

`Searchable terms` в замеренных вызовах состоял в основном из слов вроде
`something`, `anything`, `exactly`, `nothing`, `carefully` — словаря, который не
помогает адресовать ничего. `Showing N of M` — отдельная статья: это не накладной
расход, это **одиннадцать приглашений сходить за тем же ещё раз**, см. D8.

## D4. Проза в `inputSchema`

После сжатия описаний (#4, ADR-0014) основной вес постоянной поверхности несут
схемы: 12 359 симв. против 6 402 симв. описаний. **55% схемы (6 784 симв.) —
это `description` параметров.**

```
401  "Label of ONE indexed source. Pairs with confirm:true to delete…"   ← ctx_purge
289  "Keep the process alive past the timeout (servers, daemons)…"       ← ctx_execute
226  "Scope for `queries`. `batch` searches only the chunks…"            ← ctx_batch_execute
214  "Explicit scope selector. 'session' REQUIRES sessionId…"            ← ctx_purge
205  "UUID of a single session. Pairs with confirm:true to wipe…"        ← ctx_purge
```

Три из пяти худших принадлежат `ctx_purge` — инструменту, который вызывают раз в
жизни и который платит за свою документацию в каждом запросе. Правило ADR-0014
(«байты, уходящие с каждым запросом, обязаны себя окупать») к `inputSchema` не
применялось ни разу.

## D5. PostToolUse-нудеж, окупаемость которого не измерена

Форк добавил впрыск, которого у upstream нет вовсе:

```
tool_response 60 KB → upstream: 0 симв.   форк: 219–272 симв.
```

Замерено прогоном обоих `hooks/posttooluse.mjs` на одинаковом stdin. Расход
реальный, эффект — гипотеза. В сессии `bc3ee44a` он сработал на первом же
`ls -la` (7,2 KB), где менять поведение было не на что.

## D6. Телеметрия не влияет на маршрутизацию

`missed-redirect` пишется в `src/session/analytics.ts`, читается человеком в
`ctx_stats`, и на этом цикл заканчивается. Данные ровно те, что нужны для
автоматики: команда, двадцать раз подряд напечатавшая меньше 2 KB, могла бы
перестать получать нудеж в этом проекте сама. Вместо этого пользователю предложено
вписать её в `safe-commands.txt` руками — то есть ввести то, что плагин уже знает.

## D7. Бюджет ответа выбирает инструмент, а не вызывающий

Ни один `ctx_*` не принимает «ответь в N байт». Инструмент решает сам, сколько
вернуть, а знание о том, сколько осталось окна, есть только у вызывающего.
ADR-0016 уже вводит контракт честности (ответ обязан объявлять, что он опустил);
не хватает второй половины — контракта бюджета.

## D8. Экономия считается на вызов, а не на задачу

Если ответ усечён и вызывающий идёт за остатком вторым вызовом, «экономия»
первого вызова — это перенос стоимости, а не её устранение. Текущий учёт
(`bytesAvoided`, `ctx_stats`) этого различить не может: он поштучный. 1 827 симв.
пометок `Showing N of M` в одной сессии — измеримый объём таких переносов.

## D9. Плагин перехватывает только в момент прибытия

Всё, что он проиндексировал, физически лежит в FTS5 — то есть старый
`tool_result`, всё ещё занимающий место в окне, **уже существует в виде
адресуемого указателя**. Механизм есть целиком: чанкинг, дедуп, указатели, хеши.
Нет момента применения. `PreCompact` сегодня решает задачу «пережить сжатие», а не
«управлять сжатием». Это единственный дефект в списке, чья цена растёт с длиной
сессии, а не с числом вызовов.

## D10. Правильный путь дороже по эргономике

Диагноз поставлен самим форком в BENCHMARK Part 4: *«латентность эмфатически не
причина, по которой модель тянется к Read; она избегает необходимости сочинять
программу»*. `ctx_read(path, intent)` — верный ход именно потому, что программу
писать не надо. У `Bash` эквивалента нет: `ctx_batch_execute` требует `label` и
`queries`, то есть церемонии, которой у `Bash(command)` нет.

## D11. Субагентский путь не проверен на живом агенте

Что уже есть (проверено чтением кода):

- `hooks/core/routing.mjs:1823` — ветка `Agent`: блок маршрутизации впрыскивается
  в промпт субагента (1 755 байт, цель 1,5 KB); субагенты типа `Bash` повышаются
  до `general-purpose`;
- `agents/context-gather.md` — субагент с явным списком `ctx_*` в `tools:`;
- `hooks/subagentstop.mjs` + `src/session/subagent-capture.ts` — транскрипт
  субагента дистиллируется и индексируется под `subagent:<type>:<id>`;
- ADR-0008: чтения субагента не двигают лестницу эскалации (их байты в главное
  окно не попадают).

Что **не** проверено ни одним тестом на живом агенте:

- **Бутстрап схем внутри субагента.** На Claude Code ≥2.1 схемы MCP отложены.
  Комментарий в `hooks/routing-block.mjs:55-57` прямо описывает риск: блок
  субагента не преднагружает схемы, но зовёт `ctx_*` — это режим отказа #724.
  Если субагент получит ошибку валидации, он сделает ровно то, чего плагин
  избегает: свалится на сырые `Read`/`Grep` в своём контексте.
- **Окупаемость блока.** 1 755 байт × N субагентов за сессию. При пяти субагентах
  это ~9 KB, потраченных на инструкцию, эффект которой никем не измерен.
- **Правильность капчура.** `subagent-capture` отказывается индексировать главный
  разговор, когда не может изолировать агента, — поведение верное, но частота
  срабатывания этого отказа неизвестна.
- **Гипотеза, которую никто не проверял:** субагент — более сильный firewall, чем
  песочница. Его контекст выбрасывается целиком, в родителя возвращается только
  отчёт. Возможно, для части задач правильный ответ плагина — не «напиши
  программу», а «отдай это субагенту».

# Часть II. Бенчмарки

## Три уровня, три разных вопроса

| Уровень | Вопрос | Модель участвует | Где живёт | Когда гоняется |
|---|---|---|---|---|
| **L0** | Сколько байтов стоят поверхности плагина | нет | `tests/` (vitest) | каждый PR |
| **L1** | Выбирает ли агент маршрутизированный путь | да | `tests/agent-bench/` | раз в волну |
| **L2** | Решает ли агент задачу правильно и дешевле | да | `tests/agent-bench/` | раз в волну + перед релизом |

L0 детерминирован и дёшев — он и должен быть воротами CI. L1/L2 стоят реальных
денег и стохастичны — их место в конце волны, с повторами и доверительными
интервалами, а не в pre-commit.

---

## L0 — поверхности (детерминированный, в CI)

Расширение того, что уже есть (`tests/core/tool-description-displacement.test.ts`,
`tests/hooks/sessionstart-survives-compaction.test.ts`).

**L0.1 Бюджет постоянной поверхности.** Поднять `server.bundle.mjs` по stdio,
снять `tools/list`, разложить на: описания / `description` внутри схем /
структурный JSON. Зафиксировать потолки:

```
описания (compact)          ≤  6 500   (сейчас 6 402)
проза в inputSchema         ≤  3 500   (сейчас 6 784)  ← цель D4
структурный JSON            ≤  5 800   (сейчас 5 575)
tools/list целиком          ≤ 16 000   (сейчас 22 549, upstream 29 986)
```

Тест падает при превышении. Новый инструмент обязан вписаться в бюджет или
подвинуть чей-то — это и есть механизм, которого не хватало, когда пять новых
инструментов съели выигрыш от сжатия описаний.

**L0.2 Бюджет обратного трафика.** Для фиксированного набора вызовов
(`ctx_execute` с 3-строчной программой, `ctx_batch_execute` из 2 команд,
`ctx_search` с 4 запросами) считать долю лесов в ответе классификатором из
разведки этого плана. Потолок: **≤ 10%** (сейчас 35,5%).

**L0.3 Бюджет впрысков за сессию.** Прогон реальных хуков на реальном stdin-контракте:
SessionStart + N вызовов лестницы + блок субагента. Потолки:
SessionStart ≤ 3 100, блок субагента ≤ 1 800, суммарные впрыски лестницы за 8
однотипных нарушений ≤ 1 000.

**L0.4 Отсутствие дубликата.** Тест-инвариант: ни один ответ `ctx_*` не содержит
дословно ту строку, которую вызывающий передал в аргументах (кроме меток).
Это D1 и D2 в форме, которую нельзя случайно отменить.

## L2 — задачный бенчмарк (сердце плана)

L1 описан ниже как побочный продукт L2: adherence снимается с тех же прогонов.

### Харнесс

`claude` 2.1.238 умеет `-p/--print`, `--output-format json`, `--settings`,
`--agents`, `--strict-mcp-config`, `--permission-mode` — этого достаточно, чтобы
гонять агента без человека и получать структурированный отчёт с расходом токенов.

```
tests/agent-bench/
  tasks/                 # по файлу на задачу: промпт + оракул
  arms/                  # settings.json на каждую ветку
  run.mjs                # прогон: задача × ветка × повтор
  score.mjs              # оракулы, гейты, отчёт
  results/               # сырые JSON прогонов, коммитятся
```

Каждый прогон — отдельная рабочая копия (`git worktree`) на фиксированном
коммите, чтобы задача «сделай правку» не отравляла следующий прогон.

### Ветки

| Ветка | Что включено |
|---|---|
| `off` | плагин выключен целиком: ни MCP, ни хуков, ни скиллов. Базовая линия |
| `on` | плагин как есть (default) |
| `on-lean` | плагин + правки D1–D3 (леса убраны) |
| `on-budget` | `on-lean` + `budget` как параметр вызова (D7) |
| `on-deleg` | `on-lean` + инструкция делегировать тяжёлую разведку субагенту |
| `sub-off` | задача принудительно через субагента, плагин выключен |
| `sub-on` | задача принудительно через субагента, плагин включён |

`off` обязателен и обязан быть честным: `--strict-mcp-config` без конфига плагина
плюс настройки без его хуков. Без честной базовой линии весь бенчмарк — самоотчёт.

### Задачи и оракулы

Оракул должен быть машинным везде, где это возможно. Судья-модель — только там,
где механического оракула не существует, и он обязан быть слепым к ветке.

| # | Класс | Пример | Оракул |
|---|---|---|---|
| T1 | Локализация | «где реализована лестница эскалации?» | ожидаемый путь + диапазон строк присутствует в ответе |
| T2 | Агрегация | «сколько тестов в `tests/`, сколько из них про хуки?» | точное число, посчитанное скриптом |
| T3 | Импакт | «что сломается, если сменить сигнатуру `escalationLevel`?» | множество файлов-вызывающих; F1 против эталона |
| T4 | Правка | «добавь env-флаг X, задокументируй, покрой тестом» | `npm test` зелёный + `grep` по `docs/env-flags.md` + тест существует |
| T5 | Отладка | подложенный сломанный лог сборки | причина названа верно (строгое совпадение с эталонной строкой) |
| T6 | Обзор | «объясни, как устроен капчур субагентов» | слепой судья по рубрике: 5 обязательных фактов, каждый есть/нет |
| T7 | Веб | «прочти доки X и ответь на вопрос Y» | точный факт из страницы |

Минимум 4 задачи на класс — иначе одна неудачная формулировка определит вывод.

### Метрики каждого прогона

Первичная — правильность. Остальные считаются, но не могут её перевесить.

```
correct            bool     — вердикт оракула
context_bytes      int      — всё, что вошло в окно: результаты инструментов
                              + впрыски хуков + постоянная поверхность
input_tokens       int      — из --output-format json
output_tokens      int
turns              int      — число ассистентских шагов до ответа
tool_calls         {name: n}
routed_share       float    — L1: доля тяжёлых вызовов, ушедших через ctx_*
first_call_complete bool    — понадобился ли второй вызов ради усечённого ответа
wall_ms            int
denied             int      — сколько раз лестница отказала
denied_then_failed bool     — отказ был и задача провалена
```

`context_bytes` считается разбором транскрипта прогона тем же классификатором,
что и в разведке: это единственная метрика, которую нельзя подделать
формулировкой отчёта.

### Статистика

Агент стохастичен. Один прогон не значит ничего.

- **k = 5** повторов на пару (задача × ветка), фиксированная модель.
- Правильность отчитывается как доля с интервалом Уилсона, а не как «4 из 5».
- Экономия отчитывается **только по задачам, решённым верно в обеих
  сравниваемых ветках**. Задача, проваленная в `on`, попадает в отдельный
  список регрессий и не участвует в подсчёте байтов ни в какую сторону.
- Медиана и p90 по `context_bytes`, не среднее: один прогон с флудом иначе
  съедает вывод.

## Гейты «экономия не вредит» — условие приёмки

Это ответ на первое требование заказчика. Волна не выпускается, если хотя бы один
гейт красный.

| Гейт | Условие |
|---|---|
| **G1. Непричинение вреда** | нижняя граница интервала Уилсона по `correct` в ветке `on` не ниже точечной оценки ветки `off` |
| **G2. Именной регресс** | список задач, решаемых в `off` и не решаемых в `on`, — пуст. Каждая такая задача разбирается поимённо, а не усредняется |
| **G3. Отказ не ломает работу** | `denied_then_failed` == 0 на всём наборе |
| **G4. Полнота первого ответа** | `first_call_complete` ≥ 0,9 — иначе «экономия» переносится во второй вызов (D8) |
| **G5. Шаги не растут** | медиана `turns` в `on` не больше `off` + 1 |
| **G6. Время** | p90 `wall_ms` в `on` не хуже `off` более чем в 1,5× |
| **G7. Экономия есть** | медиана `context_bytes` в `on` **строго меньше** `off` на задачах, решённых обеими. Если нет — плагин на этом классе задач не нужен, и это надо записать, а не спрятать |

G7 сформулирован так намеренно. Вероятный исход: на T1 (локализация одним `rg -l`)
плагин проиграет — это уже видно из BENCHMARK Part 4, где `ctx_find` возвращает
2,6 KB против 0,7 KB. Правильная реакция — не подкрутить бенчмарк, а сузить
область, где маршрутизация рекомендуется, и записать это в описание инструмента.

## L2-S — субагентская ветка (второе требование заказчика)

Прогоняется тот же набор задач, но задача обязана быть выполнена через `Agent`.

**Что проверяется в первую очередь — бутстрап.** Гипотеза отказа #724
формулируется как измеримое утверждение:

```
bootstrap_ok = субагент сделал хотя бы один успешный вызов ctx_*
               без предшествующей ошибки валидации схемы
```

Гейт: `bootstrap_ok` == 1 в 100% прогонов ветки `sub-on`, при
`ENABLE_TOOL_SEARCH` включённом **и** выключенном. Один провал здесь means
субагент свалился на сырые `Read`/`Grep` — то есть плагин в субагентах не
работает, как бы хорошо ни выглядели остальные числа.

**Что меряется дальше:**

| Метрика | Зачем |
|---|---|
| `parent_context_bytes` | сколько попало в окно **родителя** — единственное, что реально стоит |
| `child_context_bytes` | сколько сжёг субагент (не бесплатно, но и не в окне родителя) |
| `block_cost` | 1 755 × число субагентов — цена инструкции |
| `report_correct` | вердикт оракула по отчёту субагента |
| `capture_ok` | нашёл ли родитель через `ctx_search` факт, который субагент видел, но в отчёт не включил |

`capture_ok` — прямая проверка того, ради чего написан
`src/session/subagent-capture.ts`: задача формулируется так, что нужная деталь
заведомо не попадёт в отчёт, и родителя спрашивают о ней вторым вопросом.

**Сравнение, ради которого всё это:** `on` против `on-deleg` против `sub-on`.
Если делегирование при равной правильности даёт меньший `parent_context_bytes`,
чем песочница, — это меняет рекомендацию плагина, а не только его настройки.
Гипотеза D11 либо подтверждается числом, либо снимается.

### Стоимость прогона

Полный набор: 7 классов × 4 задачи × 7 веток × 5 повторов = 980 headless-прогонов.
Это дорого и делается раз в волну. Для повседневного прогона — конфиг `smoke`:
7 классов × 1 задача × 3 ветки (`off`, `on`, `sub-on`) × 3 повтора = 63 прогона.
Дневной smoke ловит обвал, волновой полный набор — деградацию.

# Приложение A. Стартовые условия

Дописано, чтобы план можно было начать выполнять в чистой сессии, без разговора,
в котором он родился.

**Дерево.** Ветка `main`. Форк на 67 коммитов впереди `merge-base` с upstream
(`cf251eb8508da456ace8b9e98b12153fa697b538`); upstream за это время ушёл на 4
коммита, все `ci: update install stats` — то есть функционально форк на уровне
v1.0.169 и расхождения по коду нет.

**Дерево чистое.** План (`7d85383`), поправка к нему (`a0221a6`) и волна ADR-0025
(`ad94c8d`) закоммичены; `npm test` — 255 файлов, 4893 прошло, 38 пропущено, 0
упало.

**Одна ловушка, стоившая ложного диагноза, — записана здесь, потому что она
касается всего плана.** При первом прогоне `npm test` на этой машине падали
четыре теста в `tests/hooks/platform-parity.test.ts`, включая `D1: the top of
the ladder refuses on both` — тест, который волна не трогала. Диагноз «волна
сломала верхнюю ступень лестницы» продержался ровно до проверки на чистом HEAD:
там падали те же четыре.

Причина — не в коде, а в харнессе. `envFor()` собирает окружение хука через
`...process.env`, то есть **личные настройки оператора попадают внутрь теста**. В
моей оболочке стояло `CONTEXT_MODE_NUDGE_AFTER_CALLS=8` (по умолчанию 3), и все
засеянные `seedTally` значения съехали на ступень вниз: там, где тест ждал
`deny`, лестница отвечала `guidance`.

```
npm test                                                      → 4 упало
env -u CONTEXT_MODE_NUDGE_AFTER_CALLS -u CONTEXT_MODE_NUDGE_AFTER_BYTES npm test → 0 упало
```

Для плана это не анекдот, а требование к L1/L2. **Ветка бенчмарка обязана
собирать окружение агента с нуля, а не наследовать его.** Харнесс, который
спреду́ет `process.env`, измеряет машину, на которой запущен, и делает это молча:
результат выглядит как вывод о коде. То же относится к настройкам самого
Claude Code — ветка `off` должна отключать плагин явно (`--strict-mcp-config`,
настройки без хуков), а не полагаться на то, что в окружении его нет.

Отдельно стоит починить и сам `envFor()`: перечислять переменные, которые тесту
нужны, вместо наследования всего окружения. В план это не входит, но
`tests/agent-bench/` повторять эту ошибку не должен.


**Первое действие новой сессии** — P0.1 по рецептам приложения C.


**Разведка, породившая план, проиндексирована.** Замеры выполнялись через
`ctx_execute`/`ctx_batch_execute`, значит их вывод лежит в базе знаний проекта.
`ctx_search(queries: [...], sort: "timeline")` достаёт его без повторного прогона —
это дешевле, чем мерить заново, и это же проверка того, что капчур работает.

**Первое действие по существу:** P0.1, по рецептам из приложения C.

# Приложение C. Рецепты воспроизведения

Все замеры приложения B получены так. Рецепты нужны, потому что P0.1 — это
транскрипция этих прогонов в скрипты, а не их переизобретение.

## C.1 `tools/list` обеих сборок

**Ключевой факт:** upstream трекает `server.bundle.mjs` в git, поэтому сравнение
делается на настоящем протоколе, а не оценкой по исходникам.

```bash
git show upstream/main:server.bundle.mjs > .tmp-upstream-server.bundle.mjs
```

Класть его **в корень репозитория** — Node резолвит `node_modules` вверх по
дереву, из `/tmp` бандл не поднимется.

Дальше — stdio JSON-RPC: `initialize` → пауза ~1,5 с →
`notifications/initialized` + `tools/list`, ответ ловить по `id`. Режим описаний
переключается `CONTEXT_MODE_TOOL_DESCRIPTIONS` (`compact` | `full` | пусто).
Разложение схемы на прозу и структуру: рекурсивный обход `inputSchema` с
суммированием всех `description`, остальное — структурный JSON.

Прибрать за собой: `rm .tmp-upstream-server.bundle.mjs`.

## C.2 Хуки

Прямой запуск с JSON на stdin:

```
node hooks/pretooluse.mjs  <<< '{"session_id":"…","cwd":"…","hook_event_name":"PreToolUse",
                                 "tool_name":"Bash","tool_input":{"command":"cat /var/log/syslog"}}'
```

Для upstream — `git worktree add --detach <dir> upstream/main` и запускать хуки
оттуда, но с `cwd` в основном репозитории.

**Считать надо обе полки, а не одну.** `hookSpecificOutput.additionalContext` —
очевидная; `permissionDecisionReason` — тоже входит в контекст модели, и на
лестнице форка именно она несёт текст замены (ADR-0025). Замер, считающий только
`additionalContext`, покажет форку 0 там, где он потратил 877 симв.

**Грабли, на которые я наступил.** Хуки форка и upstream делят одно хранилище
состояния, ключ — `session_id`. Если гонять обе ветки с одинаковым `session_id`,
первая гасит подсказку второй, и вторая покажет ноль на ровном месте. Разные
`session_id` на каждую ветку и на каждый сценарий.

## C.3 Транскрипт

`~/.claude/projects/<slug>/<session-id>.jsonl`, по строке на событие. Пары
`tool_use` → `tool_result` сшиваются по `tool_use_id`; текст результата лежит либо
строкой в `content`, либо массивом блоков с `.text`. Классификация лесов —
регулярками по началу ответа (фенсированный блок кода), по заголовкам
`## Commands` / `## Indexed Sections`, по строкам `$ `, `> **Tip:**`,
`Searchable terms for follow-up:`, `> Showing N of M`, `> Deduplicated`.

Это и есть будущий `scripts/measure-return-overhead.mjs` из P0.1: он должен уметь
и разбор транскрипта (ретроспектива), и живой вызов (регрессия в CI).

## C.4 Проверка headless-агента

`claude` 2.1.238 установлен локально и имеет всё нужное: `-p/--print`,
`--output-format json`, `--settings`, `--agents`, `--strict-mcp-config`,
`--permission-mode`. Перед постройкой P0.3 — убедиться, что версия не съехала и
`--output-format json` по-прежнему отдаёт расход токенов.
